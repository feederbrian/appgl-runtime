# Flush-Points Audit

DCR3-A rule: every CPU read of a GPU-produced result is either a flush point or
is provably reading CPU-shadow state that is already post-flush for today's
implementation.

| Entry point | Disposition | Evidence |
| --- | --- | --- |
| `glReadPixels` / aliases | Flush point | `GLContext::readPixels` flushes FBO paths via `frameGraph->flushForReadback()` before reading attachments, and default-FB paths encode pending work then call `flushForReadback()` before `copyRGBA8Pixels`. PBO destinations are resolved to shadow memory before the readback. See `src/context/GLContext.mm:14151`, `src/context/GLContext.mm:14353`, `src/context/GLContext.mm:14879`. |
| `glReadnPixels` | Flush point by delegation | `GLContext::readnPixels` validates `bufSize` and delegates to `readPixels`. See `src/context/GLContext.mm:52871`. |
| `glGetTexImage`, `glGetTextureImage`, `glGetnTexImage` | Flush point | `glGetTexImage` resolves the bound texture and calls `GLContext::getTextureImage`; `getnTexImage` also delegates there. `getTextureImage` calls `frameGraph->flushForReadback()` before reading the Metal texture and uses typed `FlushForReadback` staging blits for private/sparse/depth paths. See `src/runtime/AppGLGroup8.cpp:129`, `src/context/GLContext.mm:50445`, `src/context/GLContext.mm:50599`, `src/context/GLContext.mm:50693`, `src/context/GLContext.mm:50890`, `src/context/GLContext.mm:51229`, `src/context/GLContext.mm:52897`. |
| `glGetCompressedTextureImage` | Post-flush or CPU-upload data today | Compressed texture readback validates and reads compressed texture bytes. Current compressed storage is upload/readback storage, not a render target producer; there is no current framegraph producer for compressed texture contents. If a future GPU producer can write compressed/sparse compressed data, this entry becomes a `CpuVisibleBarrier` flush point. See `src/context/GLContext.mm:51932`. |
| `glGetTextureSubImage` / compressed sub-image | No GPU-result read today | Current implementation validates only and does not copy bytes out. If implemented as a Metal texture read, it must share the `getTextureImage` flush path. See `src/context/GLContext.mm:51911`. |
| `glReadBuffer` | State only | `glReadBuffer` updates read-buffer selection and performs no CPU read. The next readback entry point (`glReadPixels`, `copyTextureSubImage`, etc.) owns the flush. See `src/runtime/AppGLRuntime.cpp:3991` and `src/context/GLContext.mm:20653`. |
| `glGetQueryObject*` | CPU-side state today | Query results are stored in `GLQueryObject::result` and returned directly. Query-buffer variants write the CPU-side value into buffer shadow storage through `writeBufferRange`. No Metal query result is consumed today. Future GPU-backed queries must add `CpuVisibleBarrier` or a query-result fence before exposing the result. See `src/runtime/AppGLGroup8.cpp:2574`, `src/context/GLContext.mm:52969`. |
| `glFenceSync`, `glClientWaitSync`, `glWaitSync`, `glGetSynciv` | CPU-side stub today | Sync objects are opaque CPU handles; `glClientWaitSync` returns already signaled because prior work is already synchronously visible under current semantics. Future async sync objects must become flush/wait points when the client requests visibility. See `src/runtime/AppGLGroup8.cpp:1954`, `src/runtime/AppGLGroup8.cpp:1980`. |
| `glCopyImageSubData` | Flush before GPU-copy source read; CPU fallback is shadow state | GPU copy fast path calls `flushForReadback()` before allocating `CopyImageBlit`. The larger fallback copies from CPU shadow data and then invalidates/re-uploads destination texture state. Copy classes must not become async for CPU-shadow read paths until DCR3-F has GPU-dirty tracking and CPU-visible barriers. See `src/context/GLContext.mm:47207`, `src/context/GLContext.mm:17819`, `src/context/GLContext.mm:17825`. |
| `glCopyTextureSubImage*` | Flush point before source texture copy | `blitReadFBOToTextureSubImage` flushes pending source FBO work before allocating the `CopyTextureSubImage` blit. See `src/context/GLContext.mm:49861`, `src/context/GLContext.mm:49866`. |
| `glGetBufferSubData`, `glGetNamedBufferSubData` | CPU-shadow read today | These read via `readBufferRange`; non-sparse buffers copy from `readableBufferContents`, sparse buffers first sync/mask committed pages. There is no GPU-dirty buffer producer tracked today. DCR3-F must add GPU-dirty tracking plus `CpuVisibleBarrier` before compute or copy writes can be made async. See `src/context/GLContext.mm:16301`, `src/context/GLContext.mm:8992`, `src/context/GLContext.mm:49378`. |
| `glMapBuffer`, `glMapBufferRange`, DSA map variants | CPU-shadow pointer today | Mapping returns `mutableBufferContents`/shadow-backed memory. Transform-feedback mapping logs the readback, but it is not backed by a pending Metal buffer result in the current path. DCR3-F must protect GPU-written buffers before async compute/copy. See `src/context/GLContext.mm:16336`, `src/context/GLContext.mm:16355`, `src/context/GLContext.mm:49279`. |
| PBO readback destinations | Flush is owned by producing readback | Pack PBO offsets are resolved before `readPixels` and `getTextureImage` write into the PBO shadow memory. A later map/sub-data read observes CPU shadow. See `src/context/GLContext.mm:4480`, `src/context/GLContext.mm:14177`, `src/context/GLContext.mm:50627`. |
| `glFinish` | Flush/drain point | `GLContext::finish` calls `finishPendingWork`; framegraph finish commits current work with `FinishWait`, then `drainAllOutstanding(LifetimeDrain)`. See `src/context/GLContext.mm:14139`, `src/context/MetalFrameGraph.mm:5617`. |
| `glFlush`, `swapBuffers`, present | GPU flush only, not CPU visibility | These submit/present pending work asynchronously and do not expose CPU-visible GPU results. CPU reads after present still use their own readback flush point. See `src/context/GLContext.mm:14135`, `src/context/GLContext.mm:14147`, `src/context/MetalFrameGraph.mm:5596`. |
| `glGet*` state, uniforms, buffer parameters, pointers | CPU-side state | These return tracked runtime state or CPU-shadowed uniform values. They do not read Metal command-buffer results. If future paths expose GPU-written data through these APIs, they must use `CpuVisibleBarrier`. |
| Tessellation and transform-feedback CPU counts | Keep-wait | The current tessellation domain-generation/probe and vertex transform-feedback paths immediately read Shared buffer contents on CPU after dispatch. These remain `CommitAndWait` under DCR3-A. See `src/context/MetalFrameGraph.mm:5960`, `src/context/MetalFrameGraph.mm:6984`, `src/context/MetalFrameGraph.mm:9487`. |
