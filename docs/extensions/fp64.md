# ARB_gpu_shader_fp64 / ARB_vertex_attrib_64bit

The df64 emulation module lives under `src/extensions/fp64/` and owns both
`GL_ARB_gpu_shader_fp64` and `GL_ARB_vertex_attrib_64bit`. The implementation
follows the extension-module pattern: code is compiled into the default build,
while advertising and activation are controlled by a runtime opt-in.

## Module Boundary

Module split:
- `Fp64Module` owns runtime flag resolution, the Apple GPU family capability
  probe, lifecycle state, and extension-string ownership.
- `Fp64Translation` owns the legal-MSL helper substrate for df64 lowering.
- `Fp64StateBinding` owns per-context sidecar state for double uniform, SSBO,
  and vertex-attrib backing.
- `Fp64Extension` owns df64-specific GL entry-point routing for
  `glUniform*d`, `glProgramUniform*d`, and `glVertexAttribL*` behavior.

The module registers one descriptor for `GL_ARB_gpu_shader_fp64` and one for
`GL_ARB_vertex_attrib_64bit`. Both descriptors share the same availability
gate so shader double support and 64-bit vertex attributes move together.

## Capability Gate

`APPGL_FP64_EMULATION` is still a CMake option and defaults to `OFF`, but it is
now the final fallback rather than the only way to expose FP64. Availability is
resolved in this order:

1. User JSON: `APPGL_OPTIONS_JSON`, `APPGL_CONFIG_JSON`, working-directory
   `appgl-options.json`, executable-sibling `appgl-options.json`, then bundled
   `appgl-options.json`.
2. Porter environment: `APPGL_ENABLE_FP64_EMULATION`,
   `APPGL_ENABLE_GPU_SHADER_FP64`, or `APPGL_ENABLE_VERTEX_ATTRIB_64BIT`.
3. Build default: `APPGL_FP64_EMULATION`.

JSON wins over porter flags so end users can disable a porter's shipped enable
flag when needed. Boolean strings are accepted; explicit false tokens disable
the runtime gate. When the gate is enabled, `Fp64Module::isAvailable()` also
requires a Metal device that supports the Apple GPU family baseline
(`MTLGPUFamilyApple7`) unless `APPGL_DF64_FORCE_ADVERTISE=1` is set for
measurement.

## Translation Substrate

The Phase 1 substrate uses hand-ported Knuth/Dekker-style double-double
primitives in inline MSL helpers. This avoids vendoring Bailey QD code during
the foundation commit and introduces no third-party license payload. Future
phases may replace or expand the helpers after a dedicated license review.

Hard rule from the orientation probe: emitted MSL must not contain the `double`
type. The helper substrate uses:
- `uint2` for transport and exact bit payload plumbing.
- `float2` high/low values for double-double arithmetic helpers.
- `fma`, two-sum, quick-two-sum, and two-product primitives for add/multiply
  scaffolding.

The current substrate does not emit native MSL `double`. The helper layer uses
`uint2` transport and `float2` double-double arithmetic to keep shaders legal
on Apple GPUs.

## Future Hook Architecture

Phase 2: SPIRV-Cross MSL emit rewrite for FP64 to df64 lowering.
- Lower scalar, vector, and matrix double types to legal MSL aggregates.
- Lower operators, constructors, conversions, comparisons, and pack/unpack
  without MSL `double`.
- Keep lowering gated behind df64 metadata so sister shader suites are stable.

Phase 3: ShaderTranslator integration and reflection metadata.
- Detect SPIR-V/GLSL double usage.
- Mark programs requiring df64 helper injection and binding.
- Record double uniform/block/SSBO/vertex-input requirements for runtime.

Phase 4: Runtime binding shim.
- Upload double uniform backing with std140-compatible layout where applicable.
- Bind df64 helper resources at reserved slots only for programs that need them.
- Preserve existing CPU-side double readback shadows.

Phase 5: Vertex-attrib and coherence integration.
- Preserve df64 representation for `glVertexAttribL*` shader consumption.
- Do not narrow the conformance path to f32-only streams.

Phase 6: Advertising and cascade measurement.
- Flip `GL_ARB_gpu_shader_fp64` and `GL_ARB_vertex_attrib_64bit` only after the
  fp64 core group, vertex-attrib API cases, and preservation suites show
  credible pass movement.

## Cross-Extension Dependencies

The df64 module depends on shared shader translation, reflection metadata,
pipeline creation, runtime binding, and vertex-input machinery. Per Decision H4
Refinement #7, each future dependency must be validated at the affected-stage
boundary, not only at the extension API surface.

Early preservation gates should include:
- `KHR-GL46.sparse_texture2.*` preservation, especially the 1204/1204 suite.
- Sprint 20 52-cluster repair preservation.
- Sprint 19 fragment shading rate and sparse storage-image sidecar probes.
- Shader translation suites that do not use FP64, to confirm df64 metadata does
  not perturb unrelated MSL emission.
